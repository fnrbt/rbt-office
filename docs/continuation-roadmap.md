## The initial release (alpha) - the focus from 2026-11-11

The alpha is the first browser release meant for people outside the first host application: `@rbt/office` as Word and spreadsheet editors that a static web page embeds and runs entirely in the browser (no application server), with documented host APIs, a demo page and sample files. The current engineering priority is structural consolidation across this Fable product and the .NET desktop app, as ordered below. The 0.1.x releases continue through their release/adoption gates; browser-alpha scope is not a reason to defer native consumers of shared-core migrations.

**Three ways to run it, one code base** (the user's direction, 2026-11-11):
- **Embedded, no UI:** the document widget alone - a Word page view or a sheet grid that a host draws its own UI around (what the current host does today: it builds its toolbar, menus and dialogs in Solid and takes only the engines, `docs/ui-audit.md`).
- **In the browser with our UI, no server:** the widget plus a complete toolbar, menus, dialogs and panels from `@rbt/office`.
- **On .NET as a desktop app** (not Fable): the same widget and a desktop UI.

**Target architecture, not feature-parity completion:** share document/workbook models, editing sessions, format IO, layout and paint semantics across browser and .NET; keep surface/event adapters platform-specific. Both editing sessions now own shared command/history/save policy. Word has one typed DOCX package boundary; browser, Wisp and headless Spreadsheet consumers use the typed XLSX bridge. Native painters and font/image services are shared with headless tools, and browser forms use declarative controls. Widgets and the unused Grid bundle are retired. Remaining gaps include broader native UI coverage and release-candidate fidelity/performance gates. Keep the DOM grid unless measurements justify replacing it. See the [current capability matrix](#current-capability-matrix), [review plan](systematic-review-2026-11-11.md#structural-critique-and-target-boundaries), and historical [sharing audit](sharing-architecture.md).

**Current priority — structure before additional UI features (user direction):**
the delivery targets are a Fable bundle running entirely in a statically
served page, with optional bundled chrome, and a real .NET desktop application.
Neither is a wrapper around the other. No application server, Node runtime,
desktop bridge or remote conversion service may be required by the browser.
Required runtime assets must be packaged/addressable from the static deployment;
host-supplied fonts remain an explicit capability, not an implicit service.

**Backend integration is optional, not forbidden.** The Fable product exposes
host/controller hooks through which an embedding application can integrate a
backend. HTTP transport belongs to that host-supplied adapter, not to the
editing session or UI implementation. Basic editing, local document open/save,
rendering, menus, dialogs and their validation execute locally without HTTP
calls. Opening a dialog or invoking a local editor command must not fetch its
definition, options or validation from a server. Static module/font/asset
loading is distinct from backend application calls; the complete basic UI
must work with backend endpoints unavailable. Only explicitly backend-backed
host operations may depend on network access.

### Structure-first implementation sequence

This sequence supersedes the feature-pair queue and the historical migration
order in the sharing audit. The first Spreadsheet and Word session slices and
typed Word package boundary are implemented; remaining migrations are not completion claims.

1. **Spreadsheet editing session and shared commands — implemented:**
   `src/Spreadsheet/Session.fs` owns workbook state, cell entry/recalculation,
   history, revisions and saved-state/replacement identity across browser and
   Wisp. Browser per-sheet and native global undo use one shared journal;
   selective undo preserves later foreign edits and rewrites their references.
   `StructuralCommand` / `ExecuteStructural` now own row/column insertion/deletion
   and sheet add/rename/delete/move/copy/visibility, including validation and stable
   ID issuance. `FormattingCommand` / `ExecuteFormatting` own range formatting,
   format painting, borders, clearing and merge/unmerge. `NameCommand` and
   `RuleCommand` own defined-name and validation/conditional-format transactions.
   `CaptureClipboard`, `PasteClipboard` and `PasteRows` own rich capture,
   cut/reference movement, calculation and clipboard lifecycle. `DrawingCommand`
   owns picture edits and standard chart insertion with its authored part.
   OS clipboard access, HTML decoding, pointer gestures and input/navigation stay host-specific.
2. **Typed Word document/package boundary — implemented:** `WordEditorPackage`
   and `WordEditorPackageReader` feed shared `TypedDocxImport` / `TypedDocxExport`.
   Browser and .NET use the same source-preserving writer, split into model,
   splice and assembly modules. JavaScript objects/promises and filesystem/
   dialog APIs stay at the edges. Wisp Open/Save/Save As now use this path,
   retaining opaque package parts and captured save/replacement identity.
3. **Word editing session and character/paragraph/list/table commands — implemented:**
   `src/Word/Session.fs` owns document/history, typing, save/replacement identity,
   pending character formatting, story transitions and selection restoration,
   plus `WordCommand` dispatch and atomic structural transactions in browser
   and Wisp. Enter/Tab, tracked insertion, story restrictions, no-op identity
   and selection-only navigation retain the richer browser semantics.
   Character formatting uses `Execute(Character ...)`; rich clipboard and
   logical navigation also belong to the session. Transport and visual targets stay adapters.
4. **Shared view and presentation policy — consolidated baseline:**
   canonical Word document settings, native view/hit/caret scaling, shared native
   fonts/images and renderer-only paint adapters replace duplicated host policy.
   Word and Spreadsheet browser forms use shared declarative controls; dependent
   fields and disabled choices work in both spec renderers. Browser Word form
   state/definitions remain browser adapters; full native form parity is not claimed.
   DOM/canvas, native painting, IME/events, clipboard transport and scheduling stay adapters.
5. **Desktop and packaging consolidation — host cutover verified:**
   Wisp is the desktop host; legacy Widgets wrappers are retired and useful tests
   migrated. Actual packaged static-page and desktop open/edit/undo/save/reopen
   workflows passed. Headless Spreadsheet raster/PDF/layout runners now use the
   typed bridge; native font-derived geometry remains an explicit adapter.

**Completion rule for every extraction:** both runtime callers use the shared
implementation; superseded policy code is removed; relevant Fable/.NET checks
exercise the same behavioral scenarios, including history, stale operations
and preservation where affected. Verify the actual changed browser/desktop
surface, not compilation alone. Preserve public host contracts unless an
explicitly documented migration is necessary. Do not add empty Core projects,
parallel controllers, generic editor frameworks or duplicate save routes.
Keep builds serialized and memory-capped while the machine is shared.

Word footnote/endnote UI and Spreadsheet chart manipulation remain backlog,
not the next implementation pair. Fix regressions exposed by extraction, but
do not resume feature-led shell expansion ahead of these structural milestones.

## Procedures

### Layout a new machine needs
- Nothing refers to a neighbouring checkout. Every library of another Rbt repository comes from the Forge package registry at the version pinned in `Directory.Build.props`: `Rbt.Vb`, `Rbt.Text.*`, `Rbt.Pdf` for everything, `Rbt.Renderer`, `Rbt.Widgets` and `Rbt.Wisp` for the native hosts and their runners. A NuGet source for the registry with a reader token is the one thing a machine needs. To try a change in one of those libraries here, publish it (below) and bump the pin.
- `pnpm install` in each fresh checkout or worktree.
- A Playwright with a matching Chromium. On the old machine the repo's own had none, so the harnesses were run with `PLAYWRIGHT=<path to another project's node_modules/playwright/index.mjs>`; install browsers (`npx playwright install chromium`) or point `PLAYWRIGHT` likewise. On Ubuntu 26.04 the install needs `PLAYWRIGHT_HOST_PLATFORM_OVERRIDE=ubuntu24.04-x64`, and Chromium needs `libatk1.0-0t64 libatk-bridge2.0-0t64 libatspi2.0-0t64 libxcomposite1 libxdamage1`.

### Gates (run on the merged tree before every release, whatever an agent reported)
```
bash tests/run-all.sh --core          # OFFICE core TESTS: ALL MANDATORY SUITES PASSED
bash tests/run-all.sh --native        # fresh native builds, painter, Wisp and Widgets host suites
dotnet build Office.slnx -m:1 -nr:false # all 15 supported projects; no sibling repositories
pnpm run build                       # 8 x "Fable compilation finished"
```
Browser harnesses, run per branch before merging: `tools/word-browser/{run,perf}.mjs`, `tools/docx-roundtrip/roundtrip.mjs`, `tools/xlsx-browser/{run,perf}.mjs`.
The profiles report exclusions explicitly: core excludes native/browser; native excludes core/browser. `--skip-build` is an explicit freshness opt-out and propagates to formula tests. Missing mandatory suites/fixtures fail before builds; office-format suites must be registered in the runner. Browser release gates run against an installed tarball, not the source `dist`. For a shared machine, serialize heavy commands with `flock /tmp/rbt-office-heavy.lock`; the runners default to two .NET processors and disabled MSBuild node reuse.

### Release
1. Publish any changed Rbt dependencies first, bump their pins in `Directory.Build.props`, then bump `package.json` and commit the release. Version must match the tag. Release preparation and publication require a clean checkout of that exact commit.
2. Fast-forward `master` to the release commit, tag `vX.Y.Z`, then push. The Forge action (`.forge/publish-npm`) builds, packs and publishes. `FORGE_VERSION`, `FORGE_NPM_REGISTRY` and `NPM_CONFIG_USERCONFIG` are required.
3. Wait for successful registry publication (the Forge action's status) before a host bumps; a tag alone is not publication evidence.
4. Build and use the host's review harness described in `docs/review-checklist.md`. Office probes run against the parent directories containing `docs`, with initially absent output logs. Retain comparisons and capability limits with their exact input hashes. Only a real reviewer may later author `oracle.json` and run `node scripts/verify-release-oracle.mjs BUNDLE`; that is a separate fidelity attestation, never synthesized to enable internal publication.

### Host adoption
Adopting a release in a host application (bumping its `@rbt/office` pin, running its adoption harness, deciding whether to merge) is the host's procedure and is kept in the host's repo.

### Working rules that held up
- At most two build-heavy jobs at once on a 2026 workstation; a third swaps it to death.
- One topic per commit, each commit gated on its own; a test seen failing on the old code before the fix.
- Agents: one heavy process each, no sub-agents, never kill processes by name (others share the names), never build through a copy of the tree or symlinked siblings, clean tree and nothing running at the end.
- Fable traps met so far: `=` on a `Map` recurses per entry and overflows at tens of thousands (`Model.sameMap`); `Recalc.diffCells` reads the fields of fable-library's `Map` tree, and `Model.mapOfOrdered` / `remapOrdered` / `orderedEntries` read and make its nodes (the `structure-moved-maps` browser check checks the trees), so check them on a Fable upgrade; `for KeyValue` over a `Map` and `Map.add` one by one are slow at hundreds of thousands of entries; `Math.Round` ignores `MidpointRounding`; `Double.ToString` custom formats and `Regex` `Group.Index` unsupported; `String.CompareOrdinal` with offsets broken; `StringBuilder.Append(char, count)` / `Insert` missing; mutable function bindings fail; functions are re-curried across the JS boundary; optional arguments arrive `undefined`; generic record comparison is slow; very long generated JS functions are never optimised by V8 (moving hot paths out of `evalFunction` and `Recalc.run` gave 40%).
