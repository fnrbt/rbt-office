# Printed column edges: fill expansion vs true cell width (2026-11-24)

No product sources were edited.  This is an independent vector-geometry fixture
for the five Georgia 15 upright 90 % columns (widths 16.2188-16.3438) that the
layout-width cutoff prints as hashes although Excel prints the full number.

## Why this fixture

The previous probe measured the solid-fill rectangle as the cell edge.  A fill
rectangle can be inflated for coverage, so the same PDF also draws a thin black
border on every test cell.  The border and the fill are separate vector
objects in the content stream, so the true cell width and the fill expansion can
be measured independently.

Workbook: `tests/test-documents-excel/synthetic-print-column-edges.xlsx`
(generated by `tools/excel-parity/make-print-column-edges.py`; meta
`tools/excel-parity/print-column-edges.meta.tsv`).  Georgia 15 upright,
`#,##0.00` value `1234567` in row 1, `-98.41` control in row 2, index text in
row 3; every test cell has a unique solid fill and a thin black border.

| sheet | role | scale | margins (in) | test columns start | layout |
| --- | --- | --- | --- | --- | --- |
| `E90_edge` | training | 90 % | 0.4 / 0.4 | B | 40 repeated 16.2812-char columns, then 41 varied widths 15.75-17.00 by 1/32 |
| `H85_edge` | held out | 85 % | 0.25 / 0.25 | B | same layout |
| `H90_shift` | held out | 90 % | 0.7 / 0.25 | E (A-D widths 8/22/13/9) | same layout, changed page origin |

`paperSize` is pinned to Letter.  An A4 variant was substituted by the printer
driver and rendered at an effective 82.4 % scale, so paper must be pinned for
the stated scale.

## Pre-export predictions

Both prediction files were written before the export.  GeometryModel's file
(`tools/excel-parity/print-column-edges-predictions-geom.tsv`, delivered by the
peer before the PDF export) uses a different rule: Excel snaps the print-scaled
600-dpi dot width, `true W = round(round(screenPx*47/7) * scale) * 72/600`.
At 90 % it predicts 82.680 pt for the five columns; the layout conversion in the
runtime predicts 82.620 pt.  Our locked file
(`tools/excel-parity/print-column-edges-predictions.tsv`) predicted the fill
rectangle at layout+0.143 pt and the same full decisions.

## Method

`tools/excel-parity/excel-print-pages.sh` exported each visible sheet directly
from a fresh Excel 2019 open, before any activation or Page Break Preview
(protected direct-export pass; no other Excel process was touched).  The PDFs
are read as vector content streams, not raster or fill bounding boxes:

* fill: `r g b rg  x y w h re f*`
* border: the same `re f*` form in black, and stroked `m/l S` paths, at the
  actual page coordinates;
* text: Poppler word box for the row-1 run.

`tools/excel-parity/measure-print-column-edges.py` maps each unique fill colour
to its column and pairs the fill edges with the nearest black border
centreline.  `analyze-print-column-edges.py` summarises predictions, adjacent
edges, page-local pitch and decisions.

## Results

### 1. The five widths are full numbers, and the border is 82.68-82.71 pt

Direct measurement (`print-column-edges-results.tsv`, sheet `E90_edge`,
varied-width block; fill and border coordinates in points):

| width chars | fill x..x+w | fill width | border centreline | border width | fill-border | decision |
| --- | --- | --- | --- | --- | --- | --- |
| 16.2188 | 193.250..276.050 | 82.800 | 193.310..275.990 | **82.680** | 0.120 | full |
| 16.25 | 275.930..358.754 | 82.824 | 275.990..358.690 | **82.700** | 0.124 | full |
| 16.2812 | 358.630..441.430 | 82.800 | 358.690..441.370 | **82.680** | 0.120 | full |
| 16.3125 | 441.310..524.134 | 82.824 | 441.370..524.080 | **82.710** | 0.114 | full |
| 16.3438 | 29.280..112.104 | 82.824 | 29.340..112.040 | **82.700** | 0.124 | full |

The preceding column (16.1875) has border width 81.990 and prints `########`;
16.2188 is the first full column, exactly the transition in Excel.

The runtime's layout conversion gives 82.620 pt for all five; the measured
border width is 0.060-0.090 pt larger.  GeometryModel's scaled-dot prediction
82.680 is within 0.000-0.030 pt of the measured border.  Over the 41-column
repeated block at 16.2812, the measured border width is 82.696 pt (41 samples,
range 82.680-82.710), i.e. layout +0.076 and GeometryModel +0.016.

Fit arithmetic at the first full column (model `run = 77.640`, measured word
box `77.658`, `c = 5.017944`):

```
required W = 77.658 + 5.017944 = 82.675944 pt
layout 82.620  -> hash  (margin -0.056)
border 82.680  -> full  (margin +0.004; model-run margin +0.022)
border 82.695  -> full  (margin +0.019)
```

### 2. The fill rectangle is inflated; the border is the true width

Across all 243 measured columns:

| quantity | mean | range | n |
| --- | --- | --- | --- |
| fill width - border width | **0.1194** | 0.114..0.124 | 243 |
| adjacent fill overlap (right fill of i - left fill of i+1) | **0.1195** | 0.114..0.124 | 203 |
| adjacent border gap (border_right[i] - border_left[i+1]) | **0.000** | 0.000 | 203 |

So the fill rectangle is 0.114-0.124 pt wider than the true cell (about 0.06 pt
on each side) and adjacent fill rectangles overlap by the same amount.  Neighbouring
cells share one border centreline exactly.  The previously measured fill edge is
therefore not usable as the cell width: it overstates the true width by ~0.12 pt,
while the layout width understates it by ~0.06-0.09 pt at these widths.

### 3. Repeated equal-width block: edge i vs edge 0, page breaks and origins

Per page, the 6 equal-width cells give a least-squares pitch and a residual of
every edge against `edge_0 + i*pitch`:

| sheet | pages | pitch mean (range) | max abs edge residual | first edge per page |
| --- | --- | --- | --- | --- |
| E90_edge | 7 | **82.6951** (82.6943..82.6963) | 0.0214 | 141.08 then 29.34 on every later page |
| H85_edge | 6 | **78.0151** (78.0149..78.0158) | 0.0150 | 124.04 then 18.54 |
| H90_shift | 8 | **82.6976** (82.6971..82.7000) | 0.0157 | 314.99 then 50.94 |

The pitch is constant to 0.003 pt across page breaks.  A page break resets the
x origin (E90 page 1 starts at 141.08 after the label column, pages 2-7 at
29.34) but does not change width.  The held-out margin change translates the
origin by exactly the margin difference: E90 0.4 in -> 29.34, H90_shift 0.7 in
-> 50.94 (+21.60 pt = 0.3 in), H85 0.25 in -> 18.54 (-10.80 pt = 0.15 in).
Same-width columns on the two 90 % sheets with different origins (E90 vs
H90_shift) agree on border width to 0.030 pt (mean 0.017, the border coordinate
quantisation), while their x origins differ by 173.91 pt on page 1.  Widths are
origin- and page-break-invariant.

### 4. Held-out sheets and decisions

All 243 columns were classified from the printed word box:

| sheet | columns | fill-width model | layout (82.620) model | GeometryModel (scaled dot) |
| --- | --- | --- | --- | --- |
| E90_edge | 81 | **81/81** | 36/81 (45 false hash) | **81/81** |
| H85_edge | 81 | **81/81** | **81/81** | **81/81** |
| H90_shift | 81 | **81/81** | 36/81 (45 false hash) | **81/81** |

The 45 layout-width misses on each 90 % sheet are the 40 repeated 16.2812
columns plus the five varied columns 16.2188-16.3438; Excel prints the full
number in all 45.  H85 has no decision contrast because at 85 % the layout width
already clears `run + c` by 0.16 pt; it validates the width series
(78.000-78.030 measured, GeometryModel 78.030).  H90_shift reproduces the same
width series and the same five full decisions at a different starting column
and page origin.

## Conclusion

The false hashes are a **width-source quantisation** error, not stroke expansion
and not the content inset `c`:

* true cell width = border centreline spacing = **82.68-82.71 pt** at the five
  widths (scaled-dot rule), not the layout conversion's **82.620 pt**;
* the fill rectangle is **+0.114..0.124 pt** wider than the true cell on both
  sides and must not be used as the width;
* with the true width, `run + c` is satisfied by +0.004 pt (measured advance) or
  +0.022 pt (model run); with the layout width it is short by 0.056 pt;
* widths are invariant across page breaks, margins and changed starting column;
  only page origin translates.

A fix should take the scaled 600-dpi dot width (GeometryModel's rule) as the
printed cell width; it predicts 82.680 and matches the measured border series
within one border-quantisation step.  `c`, hash advance, alignment and the fill
rendering path need no change.
